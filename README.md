# TensorRT Nodes

TensorRT 11.x, CUDA-enabled PyTorch, and ONNX are required. Supports base SDXL UNets, including Illustrious checkpoints, fixed image resolutions, dynamic context lengths, and independent B1 execution of larger batches. ControlNet and model merges are unsupported.

Connect native **Load Checkpoint** (`CheckpointLoaderSimple`) and sequential **Load LoRA** nodes to **Export TensorRT Package (Fused Model)**. Supply matching MODEL/CLIP outputs and the checkpoint's VAE. Model-only LoRA loaders and zero, negative, fractional, repeated, and asymmetric MODEL/CLIP strengths are supported.

The exporter reads its actual ComfyUI dynamic prompt, follows native loader connections, records filenames and both LoRA strengths in order, and checks the input patchers' checkpoint reload factories. Filenames and strengths must be literal loader settings. Independent MODEL/CLIP branches are combined in a deterministic order, with zero effective strength for an unused component. Unknown transformations, different base checkpoints, and linked source settings fail explicitly; no global loader hooks or manually duplicated source configuration are used.

Version 3 records the actual MODEL, CLIP, and VAE loading dtypes in `source.load_dtypes`. Native reconstruction uses those dtypes even when launch flags change. These describe the supplied source objects; changing engine precision leaves them unchanged. A loading-dtype change requires a separate source package.

| Precision | Graph preparation |
| --- | --- |
| `fp32` | FP32 weights and computation graph; preserves TensorRT's default TF32 policy. TF32 execution is not guaranteed for every operation. |
| `fp16` | FP16 graph with existing explicit higher precision operations preserved. |
| `bf16` | BF16 graph with existing explicit higher precision operations preserved; requires SM80 or newer. |
| `fp8` | ModelOpt calibration of Linear weights and activations, followed by explicit FP8 E4M3 Q/DQ export; requires SM89 or newer. Other operations may remain in higher precision. |
| `nvfp4` | ModelOpt NVFP4 Linear quantization, block size 16, FP8 block scales, global scales, and dynamic activation quantization; requires Blackwell and a compatible ModelOpt backend. Other operations remain in higher precision. |

This follows NVIDIA's [TensorRT 11 migration guide](https://docs.nvidia.com/deeplearning/tensorrt/latest/api/migration/tensorrt-10x-to-11x-python-api-patterns.html), [precision control documentation](https://docs.nvidia.com/deeplearning/tensorrt/11.4.0/inference-library/precision-control.html), and [ModelOpt diffusion export workflow](https://github.com/NVIDIA/Model-Optimizer/blob/main/examples/diffusers/quantization/ONNX-TRT-Deployment.md).

Quantization optionally requires `nvidia-modelopt[onnx]==0.47.0`, a CUDA toolkit, and Ninja. Install these in the environment used to run ComfyUI only when needed. The test environment was isolated under `dev_temp`; the existing PyTorch/CUDA/TensorRT installation was preserved. ModelOpt 0.47's NVFP4 Triton kernel fails with the installed Triton 3.9 because block pointers were removed; 0.48rc1 still has that failure. The standalone benchmark's explicit `--modelopt-cuda` preparation mode passed full NVFP4 export/build/inference using the SDK CUDA backend with ModelOpt 0.47, PyTorch 2.15 and Triton 3.9 unchanged. Production nodes do not override SDK-global backend settings. The earlier Triton 3.6 experiment conflicts with PyTorch 2.15's declared dependency and is not a recommended production environment.

For FP8/NVFP4, supply the optional `calibration_data` filename pointing to an existing local `.npz`. Use inputs captured from representative denoising calls with this checkpoint and LoRA chain, including positive/negative conditioning, multiple prompts, and denoising timesteps. Arrays must have a leading sample dimension:

```text
latent:   [N, 1, 4, height/8, width/8]
timestep: [N, 1]
context:  [N, 1, tokens, 2048]
adm:      [N, 1, 2816]
```

Arrays must contain finite floating-point values. No random calibration data is generated by the exporter. A small or unrepresentative dataset does not establish image quality. Missing calibration, unsupported hardware, quantization failures, and unsupported operators are errors; the exporter never substitutes another precision. Builds must deserialize, execute with finite output, and expose the requested precision in TensorRT inspection before publication. Nonquantized builds also compare the execution result against the export model. Quantized builds report numerical deviation as a diagnostic, without asserting production image quality.

Patched weights are materialized through ComfyUI's state-dict API into a separate UNet in memory before ONNX tracing, resolving deferred patches without tracing the shared input model. No merged checkpoint is written.

`intermediate_directory` selects temporary disk storage, defaulting to `models/tensorrt/tmp`. Absolute paths and `~` are supported; relative paths use the ComfyUI directory. Temporary files are removed after generation; failures retain a diagnostic text file in this directory.

`keep_intermediates_in_ram` defaults to false. Enable it to keep temporary ONNX graphs, exported tensor data and verification tensors in RAM-backed `/dev/shm` during generation. This requires sufficient shared-memory space and releases the contents when generation finishes or fails; it does not cache models across executions. On systems without `/dev/shm`, select a mounted RAM disk as `intermediate_directory` with this option disabled. Final engine publication uses temporary storage on the model filesystem to preserve atomic replacement even when the selected intermediate directory is on another filesystem. Package locks live beside packages under `models/tensorrt/.locks`. Normal exports do not use `dev_temp`; it is reserved for tests and diagnostics.

`package_name` selects a folder under `models/tensorrt`; blank uses the checkpoint stem. Choose a separate folder for each different checkpoint/LoRA chain. Existing sources are compared directly, including LoRA order, both strengths, and source loading dtypes; a mismatch is rejected. Precision, resolution, and context profile do not change source identity.

```text
models/tensorrt/selected_model/
  manifest.json
  engines/
    selected_model_1024x1024.engine
    selected_model_1024x1536.engine
```

Engine filenames use the sanitized checkpoint stem and image dimensions only. Rebuilding a resolution replaces its engine and manifest entry regardless of precision or context limits. Different resolutions coexist. Publication uses package locks, staged replacement, and rollback on replacement failure. An interrupted process can leave a lock; the error identifies its path. Remove it only after that process has exited.

Example manifest:

```json
{
  "format_version": 3,
  "source": {
    "base_model": "selected_model.safetensors",
    "load_dtypes": {"model": "float16", "clip": "float32", "vae": "float32"},
    "loras": [
      {"name": "style.safetensors", "strength_model": 0.8, "strength_clip": 0.6}
    ]
  },
  "engines": [
    {
      "path": "engines/selected_model_1024x1024.engine",
      "image_size": [1024, 1024],
      "precision": "fp16",
      "requirements": {
        "tensorrt_version": "11.4.0.106",
        "gpu_name": "NVIDIA RTX PRO 6000 Blackwell Server Edition",
        "compute_capability": [12, 0]
      }
    }
  ]
}
```

Context profiles and tensor shapes/types are read from the engine itself. Plans require the recorded TensorRT version and GPU model/compute capability. Older manifests must be rebuilt into a new package folder; their source loading dtypes cannot be recovered reliably. Manifests contain no weight hashes, fingerprints, merged checkpoint paths, ONNX references, or build history. Keep source files available and unchanged; changing their contents under the same filenames requires rebuilding every resolution in that package.

**Load TensorRT Engine** takes `package` and returns MODEL, CLIP, VAE. It constructs a TensorRT-backed MODEL without loading a duplicate PyTorch UNet into VRAM, loads source CLIP/VAE, and reapplies CLIP LoRAs. Engine I/O is bound using actual FP32/FP16/BF16 tensor types; quantized engines retain floating-point external I/O. Unsupported resolutions and context lengths fail explicitly. Cached wrappers detect engine replacement. ComfyUI offloading releases execution contexts and engine allocations.

**Model Switcher** takes required `trigger: ANY` and `engine_model: MODEL`, and returns only MODEL. Its non-lazy trigger is a normal execution dependency. It releases TensorRT contexts and engines, unloads the managed model, and reconstructs a conventional model from the original checkpoint and ordered LoRAs using native ComfyUI patching. Future TensorRT execution can deserialize the engine again. Missing checkpoint/LoRA files produce explicit errors and configured model search directories are respected.

Replace the old **Load Merged Model for Detailer** node with **Model Switcher**, reconnect its trigger, and rewire consumers of the removed IMAGE output. The loader's old integrity-hash option is removed.

Run tests with ComfyUI's Python from the ComfyUI root:

```sh
python custom_nodes/TensorRTNodes/tests/test_regressions.py
python custom_nodes/TensorRTNodes/tests/test_quantization.py
python custom_nodes/TensorRTNodes/tests/test_benchmark.py
TENSORRT_TEST_GPU=1 python custom_nodes/TensorRTNodes/tests/test_gpu.py
```

GPU tests build small synthetic engines and test precision inspection, dynamic contexts, batching, replacement, output types, and repeated release/reload. They are not SDXL benchmarks. Set `TENSORRT_TEST_PRECISIONS=fp32,fp16,bf16` to test a subset when optional quantization dependencies are unavailable. Test artifacts stay under `dev_temp/tensorrt`.

## Validation and measured performance

The follow-up [performance investigation](PERFORMANCE.md) includes a reusable `benchmark.py` CLI, contention logs, graph/tactic comparisons, held-out numerical checks and matched builder experiments. On the same 1024×1024 workload, optimization level 3 reduced FP16 from 100.16 to 25.52 ms and NVFP4 from 65.42 to 22.31 ms; BF16 measured 25.90 ms. Preserving Half attention in FP8 Linear exports restores fused MHA and improves level-0 latency from 101.00 to 84.13 ms; rebuild FP8 engines to use this change. These observed-idle shared-GPU measurements use different conditions from the historical table below. FP8 level-3 builds produced nonfinite outputs and remain unresolved. Quantized generation drift remains substantial, so speed does not establish production image quality. The existing UI defaults remain level 3 and 1024 MiB workspace.

Validated on 2026-10-28 with an RTX PRO 6000 Blackwell Server Edition (SM 12.0), TensorRT 11.4.0.106, PyTorch 2.15.0+cu132, ONNX 1.23.2, and driver 615.71.10. Quantization used ModelOpt 0.47.0; NVFP4 export required the isolated Triton 3.6 experiment described above. The implementation follows TensorRT 11's [strongly typed graph and explicit quantization requirements](https://docs.nvidia.com/deeplearning/tensorrt/latest/api/migration/tensorrt-10x-to-11x-python-api-patterns.html).

The full SDXL UNet was `cocoIllustriousNoobai_v55.safetensors`, with ordered LoRAs `add_contrast_XL.safetensors` (MODEL 0.8, CLIP 0.6), `add_brightness_XL.safetensors` (-0.3, 0.4), repeated `add_contrast_XL.safetensors` (0.2, -0.1), and `add_saturation_XL.safetensors` (0, 0). All engines used 1024×1024 images, batch 1, context profile 77/77/154, builder optimization level 0, and 256 MiB workspace. These settings differ from the UI's default optimization level 3.

Timing used identical inputs, CUDA events and synchronization, three fresh processes per precision, ten warmups followed by thirty measured calls per process. Median and p95 pool all ninety calls. The GPU was shared with vLLM and concurrent validation work; timing and observed free-memory deltas are approximate. Resource contention caused out-of-memory failures, including a later FP32 retry that could not allocate its 1.54 GiB execution context; the table uses completed runs. Build time includes engine validation. RMSE compares the same deterministic Gaussian workload against native PyTorch FP32 computed on CPU; it measures numerical execution differences, not image quality.

FP8/NVFP4 calibration contained eight real denoising inputs from one prompt and four steps. That is smoke calibration, insufficient to establish production image quality. Their numerical results above are diagnostics only. All five engines deserialized and produced finite `[1,4,128,128]` outputs; the ComfyUI wrapper returned FP32 tensors. Engine inspection confirmed the requested internal types. BF16 was fastest here; FP8 did not improve latency over FP16, and NVFP4 remained slower than BF16. These results do not establish performance at other profiles, optimization levels, or on an idle GPU.

Validation passed 48 regression tests, 10 calibration/quantization tests, and two GPU integration tests. The GPU suite also passed inside a real ComfyUI `PromptExecutor`. Native-loader comparisons matched all 722 patched MODEL tensors and 264 patched CLIP tensors exactly. DynamicVRAM materialization and reconstruction passed with exact checked weights and finite engine output. A fresh 1024×1024 export → load → three-step Euler sampling → VAE decode → Model Switcher run passed, including IMAGE/LATENT/STRING/INT/FLOAT triggers and reuse after release; its first sampler call took 15.678 s including model/context loading. Standalone integration scripts emitted existing ComfyUI patcher destructor warnings at interpreter shutdown.

A separate FP16 sampling comparison at 77 and 231 context tokens completed with finite decoded images and released engines. Its three-step latent relative RMSE against native sampling was 3.45% for the short prompt and 3.78% for the long prompt; matching the attention backend gave 4.62% for the short prompt. This exceeded the harness's 3% target, so full-generation numerical equivalence is not established. A real BF16 `PromptExecutor` workflow including checkpoint loading, CLIP encoding, three sampling steps, VAE decoding, and Model Switcher completed in 7.406 s; this was a single cold run.

Two additional fresh-process 1024×1024 `PromptExecutor` workflows completed for every precision, including decoded-image checks and source reconstruction. Median elapsed times from those two runs were FP32 9.988 s, FP16 7.105 s, BF16 6.994 s, FP8 13.262 s, and NVFP4 7.862 s. Shared-GPU variation was substantial; a third-round FP32 attempt failed to allocate its execution context. These few cold runs do not establish steady-state generation throughput.

A final 1024×1024 workflow passed for all five precisions with launch flags forcing FP8 MODEL loading, FP32 text encoding, and FP16 VAE loading while the recorded source policy was FP32 MODEL, FP16 CLIP, and FP32 VAE. All three recorded dtypes were preserved; decoded images were finite and Model Switcher returned the original MODEL dtype. These were single verification runs, not additional throughput measurements.

Compact measurements, scripts, and diagnostics remain under `ComfyUI/dev_temp/tensorrt/review`. Owned benchmark engines, ONNX intermediates, external data, and calibration arrays were removed after validation. Existing legacy packages are left intact and require rebuilding before use with these nodes.
